# e2e-стенд goswitch (живая GNOME-сессия)

Скелет стенда фазы 1 (гейт M1 «событие видно в логе», TEST-02/TEST-03) и
кейсы живучести (INTEG-04/05). Раннер — Go-CLI (`go run ./test/e2e`), НЕ
`go test`: наблюдаемое существует только в реальной сессии GNOME Wayland,
поэтому у стенда собственный контракт выхода — `PASS <case>` / `FAIL` и
код выхода ≠ 0 при любом провале.

## Прогон

Канонический запуск — задачами mise (D-09):

```console
$ mise run e2e-m1             # гейт M1: ключи и решения FSM в логе (TEST-02/03)
$ mise run e2e-ibus-restart   # INTEG-04: рестарт ibus-daemon переживается перерегистрацией
$ mise run e2e-kill9-survive  # INTEG-05: kill -9 демона не роняет ввод стола, respawn
$ mise run e2e-d01            # D-01: матрица проб переключения источника (план 01-04)
$ mise run e2e-chromium-smoke # 02-02: драйвер chromium — свежий инстанс, ввод→readback
$ mise run e2e-gte-smoke      # 02-02: драйвер gnome-text-editor — standalone-инстанс, ввод→readback
$ mise run e2e-word          # 02-03: трассер коррекции — ghbdtn→привет в zenity сквозным конвейером
$ mise run e2e-word-space    # 02-03: геометрия D-13 — слово после пробела, ghbdtn␠→привет␠
$ mise run e2e-word-ru       # 02-04: флип→RU-набор привет→тап-тап→ghbdtn — второе направление
$ mise run e2e-word-mixed    # 03-01: смешанное слово gfbпривет конвертирует чужой прогон → паипривет (D-23, сукцессия D-16)
$ mise run e2e-ladder-chromium # 02-05: лестница в chromium — фактический уровень + verify-after из -debug-лога
$ mise run e2e-reset-escape  # 02-05: сброс буфера по Escape (CORR-09) — поле не тронуто, отказ empty-buffer в логе
```

Напрямую (то же самое, что делает mise):

```console
$ go run ./test/e2e -case m1-gate
```

Флаги:

| Флаг       | Значение                                                                |
|------------|------------------------------------------------------------------------|
| `-case`    | `m1-gate` \| `ibus-restart` \| `kill9-survive` \| `d01-probe` \| `chromium-smoke` \| `gte-smoke` \| `word-en-ru` \| `word-after-space` \| `word-ru-en` \| `word-mixed` \| `phrase-en-ru` \| `phrase-mixed` \| `ladder-chromium` \| `reset-escape` |
| `-pacing`  | мс между инжектируемыми нажатиями ydotool (дефолт 40; поднять на нагруженной машине) |
| `-log`     | путь лога демона (дефолт — temp-файл, удаляется в teardown)             |
| `-helper`  | путь AT-SPI-хелпера (дефолт `test/e2e/focus_helper.py`)                 |

Все четыре задачи живой сессии НЕ входят в `mise run ci` — headless-CI не может
их исполнять. Каждая Go-задача, производящая код стенда, закрывается
тройным гейтом `mise run ci` (build + test -race + golangci-lint, D-08);
живой прогон — проверка интеграции, не TDD (наблюдаемое существует только в
живой сессии; класс задачи заявлен явно, D-07).

Раннер сам: собирает и запускает `goswitchd` как subprocess с `-debug`
(stderr → лог-файл), ждёт `component registered`, исполняет кейс и ВСЕГДА
разбирает окружение за собой (teardown). Помощник `waitForLog`/`waitForNew` —
поллинг лога с малым интервалом, никаких фиксированных sleep.

## Матрица v2 (план 03-07, критерий №5 фазы 3)

Полная широта жестов фазы 3 — фразы (однородные/смешанные/регистры/хвост/
long-phrase), выделение (обе геометрии Pitfall 6, частичный диапазон,
фактическая ступень per-surface), комбо, одиночный тап, super-space,
reload (валидный + битый last-good, через goswitchctl), MACR:

```console
$ mise run e2e-matrix-v2   # 21 кейс: zenity + chromium + gnome-text-editor
```

Схема шагов расширена видами `select` (каноническое имя селект-инъекции;
на поверхностях с якорем шаг гейтится на АКТИВНЫЙ пуш — чистые
перемещения каретки тоже пушатся, «какой-то новый пуш» не оракул),
`combo` (каноническая строка биндинга, гейт на записи combo+mode) и
`reload` (фрагмент конфига, применяемый по ключу к temp-конфигу кейса +
ожидание applied/rejected; применение гоняется ЧЕРЕЗ goswitchctl —
INST-02) плюс поле кейса `expect_sel_step` (фактическая ступень замены
выделения из спайк-таблицы 03-03: degraded | delete-commit |
commit-replaces; окно проверки — ДО первой коррекционной записи,
поскольку сама коррекция порождает транзитные активные пуши).
Имена инъекций канонизированы живыми пробами (Pitfall 5): ctrl+a,
SHIFT_R+CTRL_R, super+x, home, shift+right — строчные формы; KEY_-префикс
ydotool 0.1.8 НЕ понимает (фолбэк на первую букву).

Строки исключения (не молчанием): clipboard-ступени в v2 НЕТ — спайк 03-03
не нашёл поверхности с несовместимостью первичной ступени (рунг недостижим
на этом столе), механику несёт кейс `select-clipboard`.

Формат кейса — multi-doc YAML (`---`-разделители), декодер СТРОГИЙ
(`yaml.v3 KnownFields`): неизвестное поле, отсутствующее обязательное
(`name`/`surface`/`mode`/`steps`/`expect_text`), значение вне словаря
(`surface` ∈ zenity|chromium|gnome-text-editor, `mode` ∈ en|ru,
`tap` ∈ single|double|triple, `key` ∈ space|Escape|Enter|Tab) — ошибка
декодирования с номером и именем кейса, никогда не тихий пропуск.

```yaml
name: word-after-space
surface: zenity
mode: en                 # ru = раннер флипает движок в RU ДО шагов (после открытия поверхности)
steps:
  - {type: "ghbdtn"}     # ydotool type — физический путь
  - {key: space}         # пробел идёт typing-путём: имя "space" у ydotool 0.1.8 = физическая S
  - {tap: double}        # двойной Right Shift; раннер ждёт {"msg":"action","n":2} в логе
expect_text: "привет "   # руна в руну: AT-SPI readback поля (или stdout-оракул закрытого диалога)
expect_level: 1          # 0 = не проверять; иначе ФАКТИЧЕСКИЙ уровень лестницы из -debug-лога (ADR-003)
```

**Изоляция кейса — явный шаг прогона.** Каждый кейс исполняется в полном
цикле `setupStand → кейс (под watchdog 180 с) → teardown` — СВЕЖИЙ ДЕМОН
на каждый кейс. Причина: scriptMode и буфер живут в демоне — `word-ru-en`
и `word-mixed` оставляют его в режиме RU, и на общем демоне все следующие
en-кейсы падали бы; перезапуск даёт детерминированный старт EN/пустой
буфер, поэтому порядок кейсов в файле не влияет на результат
(проверено живым прогоном в перемешанном порядке).

**expect_level — фактический уровень, не предположение caps-бита**
(ADR-003). На этом столе (2026-09-15) все три поверхности сообщают
CapSurroundingText (caps 0x29) и применяют DeleteSurroundingText —
коррекции идут уровнем 1; уровня 2 живьём на столе нет, его контракт несёт
юнит-корпус (`TestActor_Level2NoCaps`).

**Поведение при FAIL.** Отчёт печатает `PASS <имя>` / `FAIL <имя>: ...`
по каждому кейсу, дублирует себя в `e2e-report.txt` (gitignored,
артефакт CI 02-07) и возвращает код выхода 1 при любом провале. Запись
verify-after `outcome:match` сознательно НЕ оракул матрицы: раунд сверки
демона закрывается по первому пушу surrounding text, а клиент может
запушить промежуточное (post-delete pre-commit) состояние — ложный
mismatch при верном поле (живая находка 02-06, отложенный пункт);
истина — content-exact readback.

**Один стенд на столе.** Префлайт матрицы отказывается стартовать, если
уже живёт процесс `goswitchd` или шина IBus держит осиротевшую
регистрацию имени (след оборванного прогона; лечится `ibus restart` —
кейс ibus-restart доказывает безопасность). Два параллельных стенда
печатали бы в чужие окна — запрет плана.

Ещё одна живая находка 02-06: обход дерева AT-SPI может зависнуть намертво
после серий SIGKILL поверхностей — мост gnome-shell перестаёт отвечать
реестру (перезапуск одного реестра НЕ лечит). Лечится перезапуском ВСЕЙ
шины a11y: `kill <pid at-spi-bus-launcher> <pid её dbus-daemon>` — стек
dbus-активируется заново, мосты пересобираются, прогулки снова мгновенны.
Между кейсами раннер сам ждёт «затишья» (отвечающего свидетеля) —
кратковременные подвисания на репащее реестре перевариваются; стойкое
зависание — окружение стола, не кейс.

## Политика состояния: стенд мутирует живой стол, snapshot/restore обязателен

Стенд меняет состояние живой сессии; teardown восстанавливает его при любом
исходе — FAIL, PASS, Ctrl-C (SIGTERM перехватывается, teardown отрабатывает
до выхода):

- **Оба ключа gsettings** (`org.gnome.desktop.input-sources` `sources` И
  `current`) снапшотятся до кейса и восстанавливаются в teardown.
  Восстановление — только при расхождении: запись значения-эквивалента
  всё равно триггерит пересборку источников GNOME и живьём сбрасывает
  глобальный движок (находка фазы 01-03). Активация goswitch идёт через
  IBus `SetGlobalEngine` — записей в gsettings стенд не делает, так что на
  практике ключи не трогаются вовсе.
- **Глобальный движок IBus** снапшотится и восстанавливается ПОСЛЕ
  остановки демона: ibus-daemon сбрасывает глобальный движок при смерти
  engine-компонента (находка фазы 01-03), восстановление до остановки
  демон бы отменил. В goswitch-движок стенд никогда не восстанавливает —
  только в простой xkb (fallback выводится из снапшота `sources`).
- **Поверхность ввода**: стенд активирует собственную поверхность и
  проверяет фокус до первой инжекции — текст не попадает в окна
  владельца. Основной путь — окно `zenity --entry`, свежесозданное окно
  получает фокус при отображении (фоновый grabFocus под Wayland
  отказывается: GTK4 — ошибка, GTK3 — false; живая находка фазы 01-03,
  best-effort `focus <app>` остался в хелпере). На заблокированной
  сессии окно спрятано за шитом — тогда стенд будит оболочечный ввод:
  super открывает обзор с поиском (незаблокированная сессия) или
  приглашение пароля (заблокированная); AT-SPI-свидетель видит обе как
  `PASSWORD_TEXT`. Обе поверхности уничтожают введённое (поиск — Escape,
  пароль не коммитится), окно zenity закрывается Enter и печатает
  набранное в stdout — это и есть оракул доставки для kill9-кейса
  (длина, не содержание: активная XKB-группа даёт `привет` на `ghbdtn`,
  живая находка).
- Временные артефакты (бинарник демона, лог) живут в `$TMPDIR` и удаляются
  в teardown, если `-log` не закреплён явно (T-03-03).

## INTEG-02: совместимость с keyd/xremap

Архитектурное доказательство (кейсы стенда его подтверждают): демон
**не захватывает evdev-слой** — нет ни uinput-драйверов, ни обработки
сырых событий; все клавиши идут транзитом через `ProcessKeyEvent`,
возвращающий `false` (наблюдатель). keyd/xremap работают на слое НИЖЕ
IBus — им нечего делить: их ремаппинг виден движку как обычные события,
конфликт невозможен по построению. Инжекция uinput
(`ydotool`/`/dev/uinput`) — только инструмент стенда, продуктовый код
демона её не касается (структурный гейт плана 01-01).

Ручная проверка живой keyd-сессии (автоматизация невозможна: на машине
владельца `keyd.service` стоит failed/disabled, его запуск требует root):

1. `sudo systemctl enable --now keyd` (и вернуть конфиг keyd, если нужен
   конкретный ремаппинг — например, capslock→layer);
2. активировать goswitch-источник: `ibus engine goswitch-en`;
3. убедиться, что обычный набор идёт без потерь при активном goswitch
   (транзит), а ремаппинг keyd по-прежнему применяется (проверить
   замапленную клавишу);
4. `sudo systemctl disable --now keyd` — вернуть исходное состояние.

До этой ручной проверки совместимость с keyd считается
**архитектурно обоснованной, но не подтверждённой живьём** (INTEG-02
закрывается архитектурой + этим чек-листом).

## INTEG-03: права, всё без root

Демон и стенд работают от пользователя сессии:

- членство в группе `input` — только для СТЕНДА (запись в `/dev/uinput`
  через ydotool; права 0660 root:input — штатный механизм ядра);
- доступ к IBus-сокету — файл `~/.config/ibus/bus/<machine-id>-...` с
  правами пользователя (аутентификация EXTERNAL по SO_PEERCRED);
- продуктовому демону root не нужен вообще: только D-Bus на собственном
  сокете пользователя (systemd user unit — план 01-05).
