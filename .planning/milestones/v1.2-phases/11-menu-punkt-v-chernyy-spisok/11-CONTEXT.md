# Phase 11: MENU — пункт «в чёрный список» - Context

**Gathered:** 2026-10-31
**Status:** Ready for planning

<domain>
## Phase Boundary

Динамический пункт трей-меню «Добавить ИмяПриложения в чёрный список» (MENU-01): один клик добавляет текущее наблюдаемое приложение в `autocorrect.apps_blocklist` — `regexp.QuoteMeta` имени, без дублей, потолок 64 — атомарной записью конфига с живой перечиткой; автокоррекция в этом приложении замолкает без рестарта демона. При неизвестной личности приложения пункт неактивен; демон не угадывает и не пишет мусорные паттерны вида `:1.NN`. Попутно (решение владельца 2026-10-27, подтверждено кодом): переименование super+space пункта «— смена режима» в честное «— язык».

</domain>

<decisions>
## Implementation Decisions

### Состояние «уже в списке»
- **D-01:** Когда текущее приложение уже в блок-листе, пункт показывается с галочкой (отмеченное состояние); клик по отмеченному пункту — no-op (защита от дублей обеспечивает безопасность клика).

### Свежесть имени приложения
- **D-02:** Имя приложения берётся из кэша наблюдателя фокуса (`internal/appid`); живые a11y-запросы при открытии меню НЕ делаются. Открытие меню мгновенное, цена — пустой кэш до первого focus-события после старта демона (ведёт себя как «личность неизвестна», см. D-03).

### Неизвестная личность приложения
- **D-03:** При неизвестной личности (snap, wezterm/winit, пустой кэш) пункт виден, но неактивен, **без имени приложения и без пояснительного текста** — решение владельца «не пишем ничего». Это сужает критерий 3 роадмапа («неактивен с объяснением») — владелец сузил осознанно 2026-10-31; текст роадмапа не переписывать, планировать по этому решению.

### Формулировка пункта super+space
- **D-04:** `macroChordWhat` меняется с `" — смена режима"` на `" — язык"` — тот же хвост, что у строки одиночного шифта («1× … — язык»); итоговая строка меню: «Super+Space — язык» (решение владельца 2026-10-27: super+space — тот же флип языка).

### Claude's Discretion
- **Размещение пункта в меню** (владелец: «где — решай сам»): в группе автокоррекции, сразу под тумблером «Автокоррекция» — действие относится к автокоррекции; отдельную секцию не заводить. Реестр menuID и layout-карусель расширить по существующим паттернам menu.go.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `internal/indicator/menu.go` — DBusMenu-сервер: статический каркас `menuLayout`/`menuItemProps`, реестр menuID, `AboutToShow` + `layoutRevision` для динамических обновлений, паттерн `checkProps` (галочка тумблера — для D-01), `bindingProps` (инфо-строки), сеттеры `Set*` для состояний извне
- `internal/appid` — наблюдатель фокуса: `FocusedApp`, identity = a11y-bridge namespace, сентинелы `ErrRoleUnknown`/`ErrBusClosed` (fail-closed) — источник кэша имён для D-02
- `internal/config/writer.go` — атомарная запись конфига (yaml.Node round-trip + rename) — механизм критерия 2 (golden-дифф «изменилась только новая строка»)
- `internal/config` `Autocorrect.validate` — потолок `maxAutocorrectBlocklist` (64), regex-валидация, строгий декодер KnownFields — критерии 2 и 4

### Established Patterns
- Уведомления владельцу — строками меню, не десктоп-уведомлениями (вердикт Phase 7 UAT: уведомления на этом столе невидимы) → отказ записи (потолок 64) показывать состоянием в меню
- Hot-reload ленивый (`internal/config/watch.go`): применяется на следующем клавиатурном событии — достаточно для «замолкает без рестарта»: гейт blocklist читается при армировании (`internal/session/actor.go`)
- Ленивый reload видит только rename-записи — атомарная запись writer'ом ему соответствует

### Integration Points
- Новая запись идёт через существующий writer → fsnotify watcher → ленивая перечитка конфига; отдельный канал проталкивания в actor не нужен
- Имя приложения в меню — через сеттер из сессионного слоя (владелец кэша appid), по образцу `SetCorrections`/`SetKeys`

</code_context>

## Specific Ideas
