## Установщик и uninstall

### Кто выполняет установку с нуля?

| Option | Description | Selected |
|--------|-------------|----------|
| goswitchctl install (Recommended) | Подкоманды CLI: component XML, user unit, ibus write-cache, daemon-reload + enable --now; идемпотентно; тестируемо Go-корпусом и e2e | ✓ |
| install.sh | Bash-скрипт в репо (curl | sh); привычный OSS-паттерн, но bash вне Go-корпуса тестов | |
| README-шаги | Только пошаговая инструкция; self-check/uninstall всё равно требуют дом | |

**User's choice:** goswitchctl install

### Должен ли install сам настраивать источники ввода («один хозяин», D-03)?

| Option | Description | Selected |
|--------|-------------|----------|
| Полная автоматизация (Recommended) | Ставит goswitch единственным источником (gsettings sources), прежние сохраняет для отката при uninstall; после установки всё работает сразу | ✓ |
| Регистрация + подсказка | Компонент/юнит автоматически, источник добавляет пользователь вручную; менее инвазивно, но не «works out of the box» | |

**User's choice:** Полная автоматизация

### Что проверяет `goswitchctl selfcheck` после установки?

| Option | Description | Selected |
|--------|-------------|----------|
| Сквозной живой (Recommended) | Версия → компонент в ibus → юнит active → ListActiveEngines → конфиг → источник goswitch; каждый пункт с подсказкой фикса (fail-fast стиль e2e-preflight) | ✓ |
| Базовый | Только версия, статус юнита, валидность конфига; без живых D-Bus-проверок | |
| На усмотрение | Состав проверок определяет планировщик | |

**User's choice:** Сквозной живой

### Что делает `goswitchctl uninstall`?

| Option | Description | Selected |
|--------|-------------|----------|
| Полный откат (Recommended) | Stop/disable юнит, удаление XML+юнита+кэша, восстановление источников; ~/.config/goswitch сохраняется, --purge удаляет и его | ✓ |
| Удалять всё | Включая пользовательский конфиг — чистый стол, но сжигает наработки при reinstall | |
| Только файлы демона | Источники восстанавливает пользователь руками | |

**User's choice:** Полный откат

## Методика perf-приёмки

### Как собираем статистику для p95 < 50 мс?

| Option | Description | Selected |
|--------|-------------|----------|
| Выделенный прогон (Recommended) | Отдельная mise-задача: N повторов горячего кейса, отчёт p50/p95/p99; однородная выборка | ✓ |
| Из каждого кейса матрицы | Latency пишется каждым кейсом; ноль отдельных прогонов, но выборка разнородная | |

**User's choice:** Выделенный прогон

### Что считаем «реакцией на горячую клавишу»?

| Option | Description | Selected |
|--------|-------------|----------|
| Только e2e-окно (Recommended) | ydotool→AT-SPI дословно по критерию; интервал опроса свидетеля фиксируется методикой | ✓ |
| e2e + внутренний лог | Два числа: верхняя граница + tap→commit из лога демона для диагностики | |

**User's choice:** Только e2e-окно

### Как измеряем память демона против бюджета <50 МБ?

| Option | Description | Selected |
|--------|-------------|----------|
| /proc VmHWM (Recommended) | /proc/<pid>/status: пик RSS — оракул; VmRSS в контрольных точках; ноль средевых зависимостей | ✓ |
| systemd cgroup | MemoryPeak из cgroupv2; доступность зависит от окружения | |
| /proc + systemd кросс-чек | Оба числа | |

**User's choice:** /proc VmHWM

### Где фиксируем результаты perf-измерений?

| Option | Description | Selected |
|--------|-------------|----------|
| Отчёт фазы + CI (Recommended) | Perf-прогон выгружает артефакт, числа цитируются в VERIFICATION | |
| Таблица в README | Ключевые числа видимы пользователям; ценой обязательства обновлять каждый релиз | ✓ |
| Только локально | Числа только в отчёте приёмки владельца; не воспроизводимо снаружи | |

**User's choice:** Таблица в README
**Notes:** Владелец выбрал публичную видимость чисел вопреки рекомендации «отчёт фазы + CI»; обновление таблицы становится частью релизного цикла (D-46).
