# ADR-001: Механизм переключения раскладки — two-engine против внутреннего флипа

## Status

Proposed — до чекпоинта владельца (гейт M0, план 01-04); после утверждения
статус обновляется на Accepted.

## Context

Решение CONTEXT фазы 01 (дословно):

> **D-01:** Механизм выбирается экспериментом в фазе 1, до кода
> коррекции/переключения. Проверочный вопрос: «может ли демон приказать
> системе GNOME переключить активный источник ввода?» Да → two-engine (два
> источника goswitch-en/goswitch-ru с XKB-раскладками us/ru; нативный
> значок, Super+Space, MRU). Нет → внутренний флип (один движок с
> `<layout>us</layout>`, EN/RU — внутренний режим, как в работающем
> прототипе владельца). Результат фиксируется ADR. — **Reversibility:**
> reversible — выбор происходит в самом начале фазы, до реализации
> зависимого кода

> **D-02:** Обходные пути (хаки) для программного переключения источника
> допустимы при условиях: без root, без правки системных файлов, работает
> на Ubuntu 24.04 GNOME Wayland, переживает перезагрузку.

> **D-03:** Если победит внутренний флип (вариант B) — «один хозяин»: в
> источниках ввода остаётся только goswitch, системные us/ru убираются;
> Right Shift — единственный переключатель; Super+Space ничего не
> переключает. Двойное состояние исключено. — **Reversibility:** costly —
> это пользовательский контракт модели переключения (UX + документация +
> e2e-кейсы); смена на two-engine позже потребует переучивания
> пользователей и переделки e2e

Эксперимент D-01 прогнан на живой сессии целевой машины (GNOME 46.0,
IBus 1.5.29-rc2, Wayland) кейсом `mise run e2e-d01`. Доказательная база —
`docs/adr/d01-experiment-log.md`: каждая проба с наблюдаемым (фокус-пара
движков в логе демона + скрипт последующего ввода), значение dconf
доказательством не является (Pitfall 3: keyboard.js 46 не синхронизирует
внешние изменения).

## Decision

**Побеждает вариант B — внутренний флип.**

Ни одна проба не дала двойного наблюдения «FocusOut(goswitch-en) →
FocusIn(goswitch-ru) + кириллический скрипт последующего ввода».
Механизм: один движок `goswitch` с `<layout>us</layout>`; EN/RU — внутренний
режим демона (как в работающем прототипе владельца, доказанном на этой
машине); XKB-группа сессии не меняется вовсе; скрипт выдачи управляет
коммитом исправленного текста (Фаза 2), а не системной раскладкой.

Kill-критерий two-engine и что его закрыло (журнал, прогоны 00:34–00:44):

| Кандидат | Наблюдаемый провал |
|---|---|
| `gsettings set … sources/current` | Запись принимается (dconf меняется), рантайм игнорирует: ни одного FocusIn/FocusOut наших движков, последующий ввод остаётся латиницей (2 прогона, одинаково). keyboard.js 46 не имеет обработчика внешних изменений. |
| ydotool `super+space` | GNOME-свитчер сработал мимо нас: focus_out(goswitch-en)+1, focus_in(goswitch-ru)+0 — живой список InputSourceManager не перестроился по внешней записи sources, MRU-цикл содержит только xkb-источники. |
| ydotool `alt+Shift_L` | Ничего наблюдаемого: 0/0, ввод латиницей. |
| IBus `SetGlobalEngine` (`ibus engine goswitch-ru`) | **Решающая находка:** пара фокусов движка исполняется (focus_out(en)+1, focus_in(ru)+1), но XKB-группа за внешним SetGlobalEngine НЕ следует — последующий ввод `ghbdtn` остаётся латиницей. keyboard.js 46 применяет раскладку только из собственного `InputSource.activate()`. |
| `org.gnome.Shell.Eval` | Отказ без unsafe mode: `(false, '')`. Включение unsafe mode запрещено (D-02/T-04-01) — unavailable. |
| Микро-расширение Shell | Загрузка нового расширения требует перезапуска GNOME Shell = ре-логина сессии владельца — unavailable, не выполнялось. |

## Consequences

Следствия D-03 «один хозяин» (costly — пользовательский контракт):

- В источниках ввода остаётся **только** goswitch; системные us/ru
  убираются. Right Shift — единственный переключатель; Super+Space ничего
  не переключает; двойное состояние исключено.
- **UX-документация обязана проговорить:** системный индикатор GNOME всегда
  показывает один источник goswitch и не отражает внутренний режим EN/RU —
  индикатор необучаем в варианте B, полагаться на него нельзя; компенсация
  (OSD-уведомление) осознанно вне объёма (deferred ideas CONTEXT). Момент
  переключения наблюдается только реакцией движка (Фаза 2+: лог/коммит).
- **e2e-кейсы** проверяют переключение по внутреннему состоянию движка
  (решение FSM в логе, скрипт коммита), а не по gsettings
  sources/current — чтение dconf в качестве оракула запрещено (Pitfall 3).
- Переключение «на лету» скрипта выдачи делает Фаза 2 через таблицы
  layouts (CORR-01..08), XKB-группа не участвует.

Наблюдение A3 (ре-активация после рестарта ibus-daemon, кейс ibus-restart
плана 01-03): при живом столе после рестарта ibus-daemon GNOME
ре-активирует plain-xkb источники; goswitch в gsettings sources в том
прогоне не было, поэтому стенд ре-активировал движок явно (SetGlobalEngine).
Требование к механизму (INTEG-04): после перерегистрации демон обязан
подтвердить свою активность — poke активации через SetGlobalEngine остаётся
обязательной частью цикла перерегистрации; авторе-активация по персистентно
оставшемуся в sources источнику goswitch будет проверена в M1+ и, если не
сработает, poke остаётся единственным путём.

Смягчение: SetGlobalEngine остаётся в арсенале стенда/диагностики (движок
переключается, ключи текут) — но механизмом РАСКЛАДКИ он быть не может.

## Reversibility

Оценки CONTEXT дословно: D-01 — **reversible** («выбор происходит в самом
начале фазы, до реализации зависимого кода»), D-03 — **costly** («это
пользовательский контракт модели переключения (UX + документация +
e2e-кейсы); смена на two-engine позже потребует переучивания пользователей
и переделки e2e»). Практически: до конца Фазы 2 смена решения стоит один
ADR; после появления пользователей и e2e-матрицы — переучивание и переделка
оракулов.
