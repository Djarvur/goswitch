# ADR-006: Двухдвижковое переключение — ревизия ADR-001 (Option B → Option A)

## Status

Accepted — вердикт владельца 2026-09-30 (чекпойнт Task 2 плана 05-01, ночь
2026-09-29→30): выбран вариант **d52-literal**; живые доказательства
механизма получены 2026-09-30 (план 05-05: кейсы two-source-flip,
external-flip-sync, ibus-restart и полная матрица v3 зелёные живьём в
двухисточниковой конфигурации — таблица живых исходов ниже).

## Context

ADR-001 зафиксировал Option B: внутренний флип EN/RU внутри демона при
единственном источнике `goswitch` в `sources`; XKB-группа всегда `us`, GNOME
о режиме не знает. Живые находки 2026-09-27/28 перевернули предпосылки
выбора:

1. **Индикатор невидим при одном источнике.** GNOME 46 показывает панельный
   индикатор ввода ТОЛЬКО при 2+ источниках в
   `org.gnome.desktop.input-sources sources`; с единственным
   `('ibus','goswitch-en')` его не показывает никакая настройка. Panel-свойства
   IBus (RegisterProperties/UpdateProperty, «260927-way») рендериться некуда —
   механизм остаётся в коде, но не решает проблему индикатора.
2. **ADR-001 Option B прячет режим от GNOME** — ярлык панели и XKB-группа
   не знают о внутреннем EN/RU, критерий 2 (актуальность индикатора, SWCH-03)
   при одном источнике невыполним по построению.

Владелец запер решения (дословно, 05-CONTEXT.md):

> **D-52 — двухисточниковая схема** (2026-09-28): sources = два goswitch-движка,
> флип = `SetGlobalEngine` на шине IBus (прямой D-Bus call, не subprocess),
> индикатор нативный. Это ревизия ADR-001 (Option B → Option A) — оформить
> как ADR-006 с живыми находками как обоснованием.

> **D-53 — источники обязаны быть `('ibus',...)`** (2026-09-28): xkb-источники
> обрабатываются mutter/XKB МИМО ibus-движков — демон не видит ни одной
> клавиши. Доказано живьём: при отвале движка GNOME переписал sources в xkb
> и ввод молча шёл мимо goswitch.

> **D-54 — install НЕ хардкодит пару en/ru** (2026-09-28): он читает текущие
> sources ПОЛЬЗОВАТЕЛЯ и оборачивает каждый источник пары в goswitch-движок
> его раскладки: `('xkb','us')→('ibus','goswitch-en')`,
> `('xkb','ru')→('ibus','goswitch-ru')`. XKB-layout лежит внутри EngineDesc
> каждого движка (механизм уже есть). «Раскладку выбирает пользователь» —
> install лишь оборачивает выбор.

Перед зависимым кодом исследование поставило центральный вопрос фазы
(Critical Finding, 05-RESEARCH.md): следует ли GNOME Shell 46 за внешним
`SetGlobalEngine` — upstream-код 46.0 не имеет пути от GlobalEngineChanged
к `InputSource.activate()`, а kill-таблица ADR-001 (строка SetGlobal) доказала
живьём, что XKB-группа не следует. Вопрос решён живым спайком `switch-spike`
(план 05-01): обратимое двухисточниковое окно на столе владельца, матрица
проб P1–P4, вердикт-отчёт `switch-spike-report.txt`.

## Decision

**Переключение — двухдвижковое: sources = оба goswitch-движка, флип =
org.freedesktop.IBus.SetGlobalEngine на ibus-соединении демона; вариант
d52-literal (D-52 дословно: engine-truth флип).**

Вердикт владельца (чекпойнт Task 2 плана 05-01, 2026-09-30): критерий 2
переформулируется spec-delta: «индикатор отражает активный источник при
пользовательских жестах; daemon-флип меняет ввод немедленно, ярлык — при
следующем пользовательском жесте». Само наблюдение индикатора владельцем —
«не разглядел» (вердикт unknown) — вынесено на приёмку фазы (UAT /
verify-work); проба XKB-истины осталась экологически неразрешённой (строка
таблицы ниже).

Отклонённые альтернативы (чекпойнт Task 2 плана 05-01):

- **sources-rewrite** (флип = перезапись gsettings sources: MRU[0] активирует
  индикатор+XKB+движок) — отклонена: тяжёлая dconf-запись на каждый тап Shift;
  MRU-инверсия гоняется с собственными записями шелла; каждая запись sources
  живо сбрасывает global engine (живая находка 01-03); противоречит букве
  D-52 «флип = SetGlobalEngine».
- **d52-plus-mru-seed** (D-52 дословно + mru-sources seeding только для
  login-restore) — отложена кандидатом v1.1: закрыла бы потерю режима после
  перелогина, но гонится с собственными записями шелла `_updateMruSettings`;
  исследование OQ2 рекомендует не трогать в v1.

## Consequences

- modeRU-ветка остаётся производителем скрипта при любом исходе — движковая
  safety-net (латинские keyval конвертируются сами, пока XKB-группа не
  доказанно следует). Живое подтверждение 05-05: XKB-группа НЕ следует
  (строка таблицы выше) — safety-net несёт типизацию на каждом флипе, и
  это постоянный дизайн, не временная мера.
- Флип сбрасывает контекст коррекции: SetGlobalEngine churn-ит
  FocusOut/FocusIn → буфер/FSM hard-reset («переключение раскладки
  сбрасывает контекст», как в GNOME; 05-CONTEXT) — текст, набранный ДО
  флипа, не корректируется жестом ПОСЛЕ него. Живое следствие матрицы
  05-05: ряды word-mixed/phrase-mixed (коррекция через границу флипа)
  красные по дизайну — вердикт владельца на verify-гейте фазы (WINDOWS #12).
- Демон — единственный писатель режима; шелл подтягивается (sync): sync-
  listener 05-04 потребляет GlobalEngineChanged (+ FocusIn с именем движка),
  а вердикт P4 обязывает подавление эха — собственные сигналы инициатора не
  трактуются как чужой флип (epoch/echo-тег, Pitfall 5 исследования).
- Третий xkb-источник честно выводит пользователя из-под goswitch —
  документируется в README (план 05-05, Task 2); D-53 неизменно: источники
  goswitch — только `('ibus',…)`.
- Семантика критерия 2 (SWCH-03) — spec-delta: «индикатор отражает активный
  источник при пользовательских жестах; daemon-флип меняет ввод немедленно,
  ярлык — при следующем пользовательском жесте».
- e2e-оракул: записи `"msg":"mode"` остаются байт-стабильными; добавляется
  новая запись `switch_engine` (имя движка — конфиг-литерал; D-20/D-21:
  набранный текст никогда не попадает в журнал/отчёт).
- SetGlobalEngine вызывается с жёстким дедлайном в бюджете <50 мс (Pitfall 4:
  без дедлайна заклинивший ibus-daemon stall-ит каждый keystroke); флип
  строго после settled-записей (D-36 порядок). Живая строка (05-05,
  assumption A6 честно): внутренний дедлайн 40 мс срабатывает РАНЬШЕ
  завершения КАЖДОГО живого флипа — фактическая латентность создания
  движка на шине ≈ 41–42 мс, так что каждый живой флип журнарует
  switch_engine в WARN-форме, а переключение всё равно lands внутри
  бюджета (<50 мс). e2e-оракул читает пару attempt-запись + readback.
  Кандидат на настройку дедлайна (40 → 45–48 мс, чтобы INFO-форма
  возвращалась) — решение владельца, не сделано молча.
- Рестарт ibus-daemon: активная раскладка сохраняется для shell-жестов
  (Super+Space — шелл помнит свой current); раскладка daemon-флипов при
  рестарте возвращается к текущему источнику шелла, и демон следует
  (живая находка 05-05, строка таблицы выше). Closing of the P1–P4
  re-assert question: возврат шеллом «своего» источника после рестарта
  наблюдён живьём и трактован демоном как фактическая правда (sync) —
  войны механизмов нет; пользователь возвращается на ru одним флипом.
- Матрица проб P1–P4 не закрывала re-assert сценарии (возврат шеллом «своего»
  источника после ibus-restart / password-field / sources-rewrite) —
  prohibition must_haves плана 05-01 держится: зафиксированная война
  механизмов остаётся стоп-сигналом; живая проверка 05-05 войны не
  выявила (рестарт-сценарий в строке таблицы выше); неразрешённая P3
  (XKB-истина) остаётся экологически закрытой — вопрос не переоткрылся.

## Reversibility

**costly** — архитектурная ревизия пользовательского контракта (цитата
ADR-001/D-03: «смена на two-engine позже потребует переучивания пользователей
и переделки e2e»). Практически: миграция живого install-state стола владельца
(wrap-takeover sources, план 05-02) + публичная семантика критерия 2
(spec-delta выше). Смена выбранного механизма после публикации = новая
ADR-ревизия + переделка e2e switch-оракулов. Фолбэк-лестница исследования
(sources-rewrite, mru-seed) сохранена в этом документе как документированные
альтернативы.
