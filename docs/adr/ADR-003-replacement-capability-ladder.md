# ADR-003: Лестница замены текста (capability ladder)

## Status

Accepted — гейт M0 (ревью владельца, план 01-04 Task 3) пройден 2026-09-10:
владелец утвердил ADR-пак ответом «утверждено». Решение фиксируется сейчас,
реализация — Фаза 2 (M2). До M0 носил статус Proposed.

## Context

Коррекция (§4.3 спеки) требует заменить «ровно диапазон неверного текста» —
перепечатать последнее слово / фразу / выделение другой раскладкой. IBus
даёт движку три принципиально разных механизма замены, и клиенты сообщают
свои возможности битовой картой в `SetCapabilities` (адаптер её уже
принимает и логирует). Исследование фазы 01 (Pattern 1, живая интроспекция
IBus 1.5.29 на целевой машине + чтение ibusengine.c/goibus) установило:

- `DeleteSurroundingText(offset, nchars)` — **сигнал без подтверждения** на
  1.5.29 (fire-and-forget): движок не узнаёт, применил ли клиент удаление;
- `ForwardKeyEvent(BackSpace)` — виден любому клиенту, но требует подсчёта
  удаляемого в **рунах** (не байтах) и ломается, если буфер и поле
  рассинхронизированы;
- буфер обмена (clipboard round-trip) — работает везде, но это
  деструктивная для пользовательского клипборда операция последней надежды.

Бит capabilities: `IBUS_CAP_SURROUNDING_TEXT = 1 << 5` — клиент полностью
сообщает surrounding text; именно эта поддержка отличает первый уровень от
остальных.

## Decision

Лестница из трёх уровней, выбор уровня — по битам из `SetCapabilities`:

1. **DeleteSurroundingText** — используется, когда клиент сообщил
   `IBUS_CAP_SURROUNDING_TEXT` (бит 1<<5): движок просит удалить диапазон
   перед курсором и коммитит исправленный текст. Отсутствие подтверждения
   на 1.5.29 компенсируется сверкой surrounding text до и после (повторная
   `RequireSurroundingText` + сверка позиции курсора).
2. **Backspace×N** — fallback для клиентов без бита 1<<5: `ForwardKeyEvent`
   с BackSpace N раз, где N — длина заменяемого в **рунах**. Инвариант
   «abort, не мусорить»: при любом сомнении в синхронизации буфера и поля
   (сверка из ADR-004 не сошлась; позиция курсора непредсказуема) —
   отменить замену молча, а не стереть чужой текст.
3. **Clipboard round-trip** — последний уровень для окружений, где первые
   два недоступны (терминальный класс, см. §6 Q3 спеки): сохранить
   пользовательский клипборд, вставить замену, восстановить клипборд.
   Применяется только по явной поддержке в конфигурации.

Уровень выбирается на каждую коррекцию по актуальной карте caps
конкретного input context; движок не предполагает, что все окна одинаковы.

Матрица e2e Фазы 2 обязана содержать **минимум один Chromium-кейс**,
подтверждающий фактический fallback-уровень (Chromium сообщает surrounding
text иначе, чем GTK — бит может отсутствовать или данные приходить
усечёнными); кейс фиксирует, какой уровень реально сработал.

## Consequences

- Механизм замены — пер-clients, не глобальный: e2e-матрица TEST-04 (Фаза 2)
  размечается по классам клиентов (GTK3/GTK4/Chromium/Electron/терминал).
- DeleteSurroundingText без подтверждения делает сверку после удаления
  обязательной частью протокола, а не оптимизацией.
- Backspace-уровень делает подсчёт рун частью контракта буфера (Фаза 2) —
  буфер хранит руны, не байты.
- Clipboard-уровень признан деструктивным и не включается по умолчанию.
- Реализация отложена в Фазу 2 (M2): в Фазе 1 адаптер уже принимает и
  логирует capabilities, сигналы `CommitText`/`ForwardKeyEvent`/
  `DeleteSurroundingText` в проводке есть — коду коррекции не потребуется
  трогать транспорт.

## Reversibility

Решение (состав и порядок уровней) — обратимо до Фазы 2: кода замены нет,
меняется только этот документ. После реализации Фазы 2 перестройка лестницы
затронет e2e-матрицу и протокол сверок — costly. Оценка соответствует
дискреции CONTEXT: «технические детали capability ladder … реализации в
фазе 2».
