# Техническое задание: goswitch — корректор раскладки и введённого текста для GNOME Wayland

> Статус: DRAFT v0.9 (фаза 1 SDD — создание спецификации; противоречия и открытые вопросы помечены `[Q]`)
> Владелец: Daniel Podolsky (@onokonem, Djarvur)
> Исполнитель: Hermes Agent

---

## 1. Проблема

На GNOME Wayland (Ubuntu 24.04, T2 MacBook Pro) отсутствует полноценный аналог Punto
Switcher: исправление текста, набранного не в той раскладке, и ручное переключение
раскладки удобными горячими клавишами. Существующие решения не покрывают потребность:

| Инструмент | Что не так |
|---|---|
| WaylandSwitcher (Nim) | Работает, но: форк чужого кода; чтение evdev напрямую несовместимо с ремапперами уровня keyd/xremap (EVIOCGRAB монополен); нет автотестов; бинарная поставка без исходной экосистемы |
| keyd / xremap | Только ремап клавиш; нет буферизации текста и коррекции; монополизируют клавиатуру |
| IBus-engine (Python) | Правильный уровень (не конфликтует по построению), но прежний прототип не доведён |
| xneur, PUNTO и пр. | Мертвы или неработоспособны на GNOME Wayland |

Цель — написать **свой** корректор на **Go**, по SDD, с **автоматизированным
тестированием полного цикла** (пользователь не участвует в тестировании).

## 2. Терминология и классы задач

1. **Коррекция по горячей клавише** (обязательно): перепечатать последнее слово /
   всю фразу / выделенный текст в другой раскладке.
2. **Переключение раскладки** (обязательно): по горячей клавише, с возможностью
   «переключить и перепечатать» одной комбинацией.
3. **Автокоррекция** (возвращена в объём как содержимое milestone v1.1.0 — решение
   владельца от 2026-09-27; см. §11 и ADR-007): молчаливое исправление набранного слова
   без команды пользователя — только opt-in (default off), только с white/black list
   по классам окон.

## 3. Архитектурное решение (утверждённые принципы)

### 3.1 Инъекция текста — через IBus engine, НЕ через uinput

Демон = **IBus input method engine** (Go, через D-Bus `org.freedesktop.IBus`).
IBus-движок:
- видит клавиатурные события до приложений, на уровне метода ввода — не конфликтует
  с evdev-ремапперами (keyd/xremap могут жить рядом, каждое на своём слое);
- умеет **коммитить текст** в поле ввода напрямую (`commit_text`), чем заменяет
  хрупкую эмуляцию «Backspace ×N + перепечатывание» через uinput;
- не требует grab клавиатуры: обычный набор идёт транзитом (forward), движок
  вмешивается только по горячей клавише.

Следствия (зафиксировать как аксиомы дизайна):
- Коррекция работает в любом поле ввода GTK/Qt/Chromium/Electron, где активен IBus.
- В терминалах, где IBus-предкоммит не применим, горячие клавиши коррекции
  обрабатываются, но механизм вставки — см. §6.4 `[Q]`.

### 3.2 Один демон — все функции

`goswitchd` — единый процесс: IBus engine + D-Bus сервис + наблюдение за раскладкой.

### 3.3 SDD-процесс

Работа ведётся по трёхфазной модели SDD (см. SKILL spec-driven-development):
фаза 1 — настоящее ТЗ и вопросы; фаза 2 — доработка спеки (код не открывается);
фаза 3 — реализация по спеке с гейтами качества. Изменения требований — через
spec-delta, а не правкой кода «по мотивам».

### 4.2 Направления коррекции

- EN→RU и RU→EN по позиции клавиш (ЙЦУКЕН↔QWERTY) — ПОЛНАЯ конвертация по физическим клавишам (директива владельца 2026-09-28 «изучи раскладку и сделай все как надо», суперседирует D-14 и allow-set 2026-09-27): преобразуется КАЖДЫЙ знак таблицы — буквы, скобочный ряд, запятая (клавиша «б»), точка (клавиша «ю»), «?» (русская запятая на Shift+/) и оба уровня Shift; отображение биективно — те же физические клавиши в другом режиме дают тот же текст. Знаки, отсутствующие в таблице (пробел), едут без изменений; буква без записи в таблице отказ всего слова.
- Автоопределение направления по составу буфера (какой раскладки больше букв).
- Смешанный текст: корректируется только часть, набранная не той раскладкой,
  относительно последней использованной. `[Q: определить точную семантику]`

- Смешанный текст: посимвольная инверсия раскладки — каждая буква
  переворачивается по таблице позиций клавиш СВОЕГО скрипта, независимо от
  позиции и без всякого якоря: латиница — по EN→RU, кириллица — по RU→EN;
  регистр сохраняется по руне (конструктивно, как в монораскладочном пути).
  Нейтральное правило, явно: знак, инверсия которого равна ему самому, едет
  без изменений (цифры — «5» в обеих таблицах переходит в «5»), как и знак
  без позиции клавиши (пробел); пунктуация и символы с позицией клавиши
  внутри СМЕШАННОГО диапазона также едут как набранные — посимвольное
  направление для них не определено («,» — клавиша-источник ОБЕИХ таблиц с
  разными образами), в отличие от монораскладочного диапазона, где
  пунктуация по-прежнему конвертируется вместе со словом. Буква,
  отсутствующая в таблице своего скрипта (é), молча отклоняет ВЕСЬ диапазон
  (продолжение D-20 — частичный вывод невозможен). Однораскладочный текст
  сохраняет прежнюю полную конвертацию без изменений — автопределение
  направления, пунктуация со словом, всё §4.2 выше; геометрия замены
  диапазона и сохранение регистра (§4.3) работают с инверсией без изменений.

### 4.3 Поведение коррекции

- Замена без визуального «прыжка»: `commit_text` заменяет ровно диапазон
  неверного текста `[Q: подтвердить возможность замены диапазона в IBus API]`.
- Сохранение регистра: `GHBDTN`→`ПРИВЕТ`, `Ghbdtn`→`Привет`, `ghbdtn`→`привет`.
- Не трогать: URL, e-mail, пути, hex-строки — по настраиваемым эвристикам (v2).
- После успешной коррекции, изменившей текст (слово, фраза ИЛИ ВЫДЕЛЕНИЕ — расширение по отчёту владельца 2026-09-28), внутренний режим скрипта переключается вслед за коррекцией — строго после записи о завершении (порядок D-36); по умолчанию включено, отключается ключом `correction.flip_after_correction`; исход «done без изменений» и любой отказ раскладку никогда не переключают (решение владельца, 2026-09-27).

### 4.5 Коррекция клавиатурных макросов

- Замена сочетаний Super+Буква на Ctrl+Буква на лету в определенных приложениях:
  нужно для того, чтобы системно заменить Ctrl+C, например, на Super+C,
  чтобы одно и то же сочетание управляло буфером обмена единообразно во всех приложениях
  (в терминале, например, Ctrl+C зянят).

Ревизия (2026-10-05, фаза 8 — a11y-магия приложений): решение владельца
D-8-1 — приложениям, для которых доступность включалась вручную (прецедент
ZCode), нужна не запись в документах, а секция в конфиге; механика применения
исследована при планировании live-пробами на целевом столе (D-8-2). В конфиг
вводится новая top-level секция `a11y` (D-8-1 предлагал «секцию типа
`a11y.apps`»; ревизия фиксирует канонические имена ключей): `a11y.enabled` —
логический ключ, по умолчанию выключен; `a11y.apps` — список RE2
regex-паттернов имён приложений, потолок 64 записи, анкеровка `^…$` явная,
все паттерны компилируются и проверяются при загрузке конфига. Нулевое
значение секции — off (zero-value = off; прецедент D-54, секция
`autocorrect`): документ без секции `a11y` загружается как прежде, поведение
демона не меняется.

Магия доступности — минимальный набор D-8-6. Когда секция активна
(`a11y.enabled` включён и список `a11y.apps` непуст), демон приводит в
значение `true` две ручки окружения: глобальный ключ gsettings
`org.gnome.desktop.interface toolkit-accessibility` (тот самый, что
включался вручную для ZCode) и, как пояс, свойство
`org.a11y.Status.IsEnabled=true` шины доступности — D-Bus вызов
`Properties.Set` на `org.a11y.Bus` (session bus). Обе операции идемпотентны:
для ключа — «прочитать, сверить, записать только при расхождении»; пояс
действует до конца сессии (session-scoped) и снимка не требует. Демон ставит
обе ручки, поэтому контракт выполняется при любой композиции стартовых
проверок приложений Chromium/Electron. Приложение получает
accessibility-дерево при следующем запуске приложения: Chromium и Electron
проверяют ключ однократно при своём старте и не подписываются на его
изменения — это семантика механизма, а не его ограничение.

Момент применения — демон-reconcile (D-8-3): при старте демона и на каждом
hot reload конфига демон идемпотентно приводит состояние окружения к
состоянию из конфига. Установка (goswitchctl install) сама ничего не
применяет и конфиг не пишет (решение 04-02, adopt+watch: генерация
документа — только действие пользователя) — секция `a11y` появляется в
конфиге лишь из документа владельца; полный документ, созданный
тумблером меню или «Настройки…», несёт её выключенной.

Откат (D-8-4): удаление приложения из списка и выключение `a11y.enabled`
ключ `toolkit-accessibility` НЕ снимают — вручную включённое владельцем
состояние неотличимо от включённого goswitch, поэтому динамическое снятие
ключа при выходе приложения из списка не предусматривается. Единственный
путь отката — `goswitchctl uninstall`: пред-установочное значение ключа
снимается дословно (verbatim) в `install-state.json` при установке и
восстанавливается только если поле в файле есть (restore only-if-present);
старый файл состояния без этого поля — предупреждение и пропуск, никогда не
«восстановить выключенное». Пояс session-scoped откату не подлежит.

Безопасность (ASVS V5): список `a11y.apps` никогда не попадает в аргументы
команды gsettings (argv) — он выбирает, выполняется ли фиксированное
действие; аргументы команды рендерятся только из литералов схемы и имени
ключа.

Резолюция по per-app механизмам (D-8-2/D-8-6): пользовательские оверрайды
запуска отдельных приложений (user-level `.desktop`-файлы с флагами запуска,
snap-оверрайды) — механизм документируется, вне v1-дифа: глобальный ключ
покрывает прецедент ZCode после перезапуска приложения; рецепт приведёт
docs/CONFIG.md. Секция `a11y` только расширяет множество приложений, у
которых есть accessibility-дерево; контракт автокоррекции §10–§11 остаётся
без изменений.

## 7. Автоматизированное тестирование (критическое требование)

Полный цикл без участия человека. Два уровня:

### 7.1 Unit / golden (CI, headless)
- Раскладочные таблицы: EN↔RU по позициям, регистры, знаки.
- Детектор направления на корпусе слов.
- Парсер конфига, hot reload.
- Чистая логика буфера: подача событий (клавиша→буфер), фиксация решений.

### 7.2 End-to-end (машина с сессией GNOME, автоматом)
Стенд-скрипт (Go + shell), который:
1. Поднимает чистый контекст: активирует окно редактора через AT-SPI/WM.
2. Инжектирует нажатия **физическим путём** (ydotool/uinput) — тот же путь,
   что у живой клавиатуры, проходит через все слои.
3. Читает результат из поля редактора через AT-SPI.
4. Сравнивает с ожиданием; матрица кейсов в YAML (ввод → ожидание):
   `ghbdtn`+Pause→`привет`; `GHBDTN`+Pause→`ПРИВЕТ`; фразы; выделение;
   смешанный текст; разные приложения (gnome-text-editor, gedit, Chrome).
5. Печатает отчёт PASS/FAIL по кейсам, код выхода ≠ 0 при падении.

Приёмка фазы 3 = зелёная матрица e2e + ручная приёмка владельцем (одна сессия).

### 7.3 Стендовые требования
- Утилиты: `ydotool` (или собственный инжектор на uinput), `at-spi` (python3-gi).
- Известная ловушка: тест обязан сам активировать целевое окно перед кейсом
  (фокус непредсказуем при ручном использовании машины параллельно с прогоном).

Решение владельца (2026-10-04, ревизия D-53): автокоррекция исправляет
тогда и только тогда, когда включена (`enabled`), полевой role-гейт

Дополнение владельца (2026-10-05, «делай» — переделка звука): тоны
играются из стандартной звуковой темы рабочего стола — резолв по XDG
Sound Theme and Naming Spec (имя темы из `org.gnome.desktop.sound`,
читается на старте демона, изменения отслеживаются — полностью
асинхронно с воспроизведением: путь звука никогда не ждёт ни чтения
настроек, ни декодирования). Воспроизведение — через ПОСТОЯННОЕ
соединение демона со звуковым сервером по нативному протоколу (чистый
Go: jfreymuth/pulse + jfreymuth/oggvorbis, см. §5), не субпроцессом на
каждый тон — механизм блока 2026-10-04 выше снят этим решением.
Синтезированные тоны остаются фолбэком, когда PCM темы ещё не готов
(старт демона, смена темы) — путь воспроизведения никогда не ждёт.
Выключенный звук (ключ конфига, тумблер «Звук» или выключенное
системное `event-sounds`) = соединения со звуковым сервером НЕТ вовсе:
ленивое подключение при включении, разрыв при выключении. Недоступный
звуковой сервер — мгновенный чистый отказ: одна WARN на эпизод, дальше
тишина, best-effort. Целевая задержка: тон слышен сразу после флипа
(~30 мс на прототипе против ~150 мс у субпроцесса).

Дополнение владельца (2026-10-05, UAT фазы 07): принятое ограничение
role-гейта — известная (видимая) идентичность приложения вне чёрного
списка при неоднозначной роли 61 (GTK3-пароль неотличим от текстового
поля) МОЖЕТ быть исправлено автокоррекцией; это ограничение AT-SPI,
принятое владельцем на UAT 2026-10-05. Fail-closed сохранён для пары
«неизвестная идентичность + роль 61» (ревью CR-01 фазы 07, слаг
role-ambiguous); приложения без accessibility-дерева (Electron/Chromium
без режима доступности — например ZCode, Telegram snap) молчат по
конструкции, способы включения задокументированы в README и
docs/CONFIG.md.
